テストも並行したほうがいいかな

はい、テストは間違いなく最初から（Phase 1のMVPフェーズから）並行して導入すべきです。
今回のように「Web Worker」「Wasm（Rust）」「JavaScript」が複雑にデータをやり取りするアーキテクチャでは、後からテストを書こうとすると「どこが原因でバグっているのか」の切り分けが極めて困難になります。
特に、Wasmで実装する予定の「差分比較ロジック（LCS/Myers diff等）」や「空白・改行無視の正規化処理」は、テストの自動化（CI/CD）と非常に相性が良い領域です。

🧪 WebMergeで導入すべきテスト戦略

すべてを網羅する必要はありません。以下の3つのレイヤーに絞り、ステップに合わせて導入するのが最も効率的です。

1. ロジックテスト（単体テスト / Unit Test）

• 対象: Wasm（Rust）側、および文字コード判定やテキスト正規化のロジック。
• 推奨ツール: Rustの cargo test、JavaScript側は Vitest。
• 理由: 「空白無視が正しく動くか」「改行コードが混在していても正しくDiffが出るか」は、画面を動かさなくてもテキストの入力と出力だけで100%検証できるため、テスト駆動開発（TDD）がしやすいです。

2. 非同期・通信テスト（Workerのモックテスト）

• 対象: メインスレッド ⇔ Web Worker 間の postMessage によるデータ往復。
• 理由: 「数千ファイルのハッシュ計算を依頼して、進捗（%）と結果が正しく返ってくるか」のフェーズ（Phase 2〜3）でバグが出やすいため、メッセージのやり取りをテストコードで担保しておくと開発が劇的に楽になります。

3. E2Eテスト（ブラウザ操作テスト）

• 対象: ファイルをドラッグ＆ドロップして、Monaco Editorに正しく表示され、上書き保存できるか。
• 推奨ツール: Playwright
• 注意点: File System Access API（ファイルピッカーや上書き保存）はブラウザのセキュリティポップアップが出るため、通常のテストツールでは自動化が少し難しい（パーミッションの自動許可設定が必要）です。そのため、E2EテストはPhase 1の最後か、Phase 2のタイミングでの導入を推奨します。

🛠️ 開発の進め方（テストを含めた最初のステップ）

High（高性能モデル）を活かして、最初のプロジェクト作成時に「テスト環境（Vitest）が最初から組み込まれた状態」の雛形（ボイラープレート）を生成させるのがベストです。
「テストコードがあるおかげで、Rustやロジックのリファクタリングをいくらやっても壊れない」という安心感は、個人開発を最後まで挫折せずに走り切るための強力な支えになります。
